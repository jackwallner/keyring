## What survived, ranked by users reached times cost

1. SM-2: entry edit or delete never lowers the odometer; reaches every fill-up logger who corrects a reading, lasts weeks, leaks into the sale PDF, and the in-app fix instruction is a dead end.
2. MB-1: Ask to Buy and SCA purchases are told they failed. Few users, but it is the paywall.
3. SM-1: deleting any saved reading can drop the odometer below the log; self-heals at the next fill-up.
4. S3: widget says "Today" for past dues until the process next launches.
5. SM-3 (with MB-2): unit switch stamps a fake reading today and can delete the last real one.
6. S1: stale notification row in Settings until the tab is left.
7. SM-4: "Add your car" card returns after a sale.

The audit's order (SM-2, SM-1, SM-3, SM-4, S3, S2, S1) is right at the top. S3 belongs above SM-3 and SM-4 (more users, though less cost per user), S2 drops out, and MB-1 enters second.

## Product calls

All six agreed as product calls, none promoted:
- P1 same-day usage event ignored (`GarageStore.swift:357-358`): intended granularity.
- P2 no reminder prompt for a device that never adds a vehicle (`requestAuthorization` is called only at `SettingsView.swift:79` and `AddVehicleFlow.swift:103`): confirmed. The most valuable of the six for a family app, since the second member who joins never gets reminders unless they find Settings.
- P3 cached Pro offline and lapsed Pro keeping vehicles: grace by design.
- P4 recall stored before the permission check (`RecallWatcher.swift:61-62,70-71`): trade-off, the in-app banner covers it.
- P5 review cooldown stamped before the system decides: the system never reports whether it showed, so there is nothing better to stamp.
- P6 overlapping `schedule` (`ReminderScheduler.swift:144-159`): an in-flight `add` from a cancelled task can land after the newer task's `removeAll`, leaving one stale reminder. Plausible, unproved, rare; keeping it as a note is right.

## Method changes that would have prevented the errors

1. Read the SDK contract before claiming an SDK-driven state. S2 assumed RevenueCat returns a pending result; its source throws. Any claim that depends on a third-party return value should cite that library's code at the resolved version.
2. List every writer of a state before saying it never changes. S3's "forever" missed the init-time and remote-change publishes. Grep for the state's writers and for every caller of the function that writes it, including initializers and notification observers.
3. Test the invariant, not one route. SM-1 was framed as a typo route; asserting I1 after deleting any row would have found the wider trigger. For each cache, delete or edit every source in turn and assert the cache.
4. Assert the whole post-state of a transition. The SM-3 test checked only the pace and missed that `correctReading` deleted a real row. After each replayed transition, assert rows, cache and date, not just the symptom chosen up front.
5. Cite user-facing copy first, helper comments last, and quote the branch the line sits in. SM-1's `:790` is the aux branch; SM-2's `reading(of:on:)` includes the cache it is used to judge.
6. Count reach from the user's ordinary error, not the auditor's contrived one. SM-2's strongest route is a fill-up on the wrong family vehicle, which needs no prompt and is far more common than a hand-typed 62,000.
